### 실패 3종 — 원인이 다르다. 섞지 않는다

| 관측 | 원인 판정 | 조치 |
|---|---|---|
| **전량 오류** (같은 코드로 100%) | **URL · 파라미터 오류** | 즉시 중단 → 마스터에게 URL 검증 요청 → `endpoints.json` 갱신 (STEP 25a) |
| **수집 0건** (요청은 200, 결과 0) | **수집 쿼리 오류** | 쿼리 조립 규칙 확인. 사이트에 매물이 없는 것으로 단정하지 않는다 |
| **수집 정상인데 항목이 0 · NULL** | **원본이 그렇게 왔을 수 있다** | 원문 확인 후 마스터에게 안내. 파싱 오류와 구분한다 |

```
전량 오류    코드 문제로 가정한다.  차단으로 단정하지 않는다
수집 0건     성공이 아니다.  status='zero' 로 알림
            엔카에 그 차종 매물이 정말 없는 경우는 드물다
항목 0·NULL  원문을 열어 실제 값을 확인한 뒤 판정한다
            「파싱이 빠졌다」와 「원본이 비어 있다」는 다르다
```

### 항목 0 · NULL 안내 규격

**수집은 정상인데 특정 항목이 전건 0 또는 NULL 이면 다음을 함께 보고한다.**

```
항목명
현상          전건 0  /  전건 NULL  /  N건 중 M건
원문 확인      raw_response 에서 해당 경로가
                 (a) 존재하고 값도 0·null 이다      →  원본이 그렇다
                 (b) 존재하는데 값이 있다           →  파싱 누락
                 (c) 경로 자체가 없다              →  그 엔드포인트가 안 준다
표본           원문 3건의 실제 값
판정           위 (a)(b)(c) 중 무엇인가
```

**(a) 로 확인되면 그것은 결함이 아니다. 문서에 「원본 미제공」으로 기록하고 축에서 뺀다.**
**(b) 는 파싱 결함이다. 재수집이 아니라 재파싱으로 고친다.**

**v1 은 이 구분을 하지 않아** `insp_outer_json` 전건 NULL 을 「저장 연결 누락」으로 오진했다.
실제로는 (b) 였고, 원문에는 값이 있었다.

## STEP 25a — 오류 해석 원칙 · 마스터 실측 요청

### 원칙 — 차단으로 단정하지 않는다

```
같은 오류가 전량 발생하면   ①  URL · 파라미터 · 헤더가 틀렸다        ← 우선 가정
                        ②  응답 형태가 바뀌었다
                        ③  그 다음에야 대상 사이트의 차단을 의심한다
```

**「막혔다」는 결론은 ①②를 배제한 뒤에만 낸다.**
v1 은 `record` 경로 후보 5개가 전부 404 였을 때 「없는 엔드포인트」로 단정했다.
실제로는 `/open` 접미사 문제였고, 진단 API 는 존재하는데 수집조차 하지 않았다.

### 판별 기준

| 관측 | 해석 | 조치 |
|---|---|---|
| **전량 404** | 경로 오류 | URL 실측 요청 |
| **전량 200 인데 내용이 다름** | 응답 형태 변경 · 라벨 오배정 | 형식 검증(STEP 18) 확인 후 실측 요청 |
| 전량 401 · 403 | 헤더 · 인증 | 헤더 실측 요청 |
| 전량 400 | 쿼리 문법 | 쿼리 조립 규칙 확인 |
| **일부만 실패** | 개별 매물 사유 | `not_found` · `empty` 로 기록. 정상 |
| 시간이 지나며 실패율 상승 | 속도 제한 가능성 | `config` 의 간격을 조정해 재확인 |

```
전량   그 엔드포인트의 요청 100% 가 같은 코드로 실패
      → 코드 문제다.  사이트 차단이 이런 형태로 오는 경우는 드물다
```

**차단이라면 특정 IP·세션 단위로 오고, 보통 429 또는 HTML 응답이다.**
**JSON 404 가 전량이면 경로가 틀린 것이다.**
