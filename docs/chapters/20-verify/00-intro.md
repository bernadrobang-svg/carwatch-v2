## 6장 정의서

### 구조체

### ★ `fatal` 은 우리 결함에만 — 외부 데이터로 멈추지 않는다

```
판별   이 검사가 실패했을 때, 원인이 우리 쪽인가 사이트 쪽인가
      우리 쪽   →  fatal.  고쳐야 진행할 수 있다
      사이트 쪽 →  그 축·그 매물만 제외.  전체는 진행한다
```

| 성격 | 예 | 등급 |
|---|---|---|
| **코드 결함** | 형식 검증 거부 · 라벨 오염 · 근거 NULL · 배점 합 불일치 | **fatal** |
| **계약 위반** | 금지 근거 사용 · PII 가 CORE 에 · 권한 우회 | **fatal** |
| **외부 데이터** | 필드 없음 · 값이 하나뿐 · 경로 미분류 · 표본 부족 | **축 제외 또는 warn** |
| **전량 실패** | 전 요청 실패 · 수집 0건 | **fatal** ★ |

```
★ 전량 실패는 fatal 이다
  일부가 없는 것과 전부가 없는 것은 다르다
  전부면 우리 쪽(URL · 인증 · 파싱)일 가능성이 크다 (2장 STEP 25a)

★ 「값 종류 1」은 fatal 이 아니다
  한 차종만 봐서 그럴 수 있다 (8장 STEP 87)
  warn 으로 남기고 전 차종 수집 후 재판정한다
```

```
필수   새 검사를 만들 때 위 4분류 중 어디인지 먼저 정한다
금지   판단이 어려우면 fatal 로 두는 것
      그러면 외부 데이터 하나에 전체가 멈춘다.  11회 재실행이 그렇게 나왔다
```

### ★ 성격이 등급을 이긴다

```
kind = 'external'          →  severity = 'warn'
kind = code · contract · total  →  severity = 'fatal'
```

```
필수   kind 를 정하지 않으면 Check 생성이 거부된다 (ValueError)
금지   severity 를 직접 지정하는 것.  성격에서 유도된다
근거   손으로 적으면 판단을 미룬다.  분류를 강제하면 미룰 수 없다
검증   V4-19  성격 없는 Check 가 없는가
```

```
★ 손으로 적은 등급과 성격이 어긋나면 성격이 이긴다
  실제로 어긋난 것 — V1-07 · V4-06 은 fatal 이었으나 external 이다
  V1-08 은 total 이라 fatal 이 맞았다
```
