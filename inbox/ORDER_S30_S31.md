# 1. 「검사가 너무 많은데 정리가 가능할까」

## ★ 지금은 셀 수가 없습니다

```
docs/CHECKS.md 가 비어 있습니다
★ 몇 개인지 · 어디 있는지 · 규격과 맞는지 아무도 모릅니다
```

## 먼저 `CHECKS.md` 를 기계로

```
필수   validate/ 에서 Check(...) 를 뽑는다
필수   docs/ 에서 「검산 V?-nn」 · 「S nn」 을 뽑는다
필수   둘을 잇는다
       | 코드 | 무엇 | 규격 위치 | 소스 파일 | 등급 | 마지막 통과 | 마지막 실패 |
필수   ★ 마지막 통과·실패 시각을 함께
       ★ 한 번도 안 돈 검사가 드러납니다
```

## 다섯 갈래

```
① 중복        같은 것을 두 검사가 본다
② 죽은 검사    통과도 실패도 한 적 없다
③ 못 잡는 검사  있는데 결함이 지나갔다  ★ V11-78 이 그랬습니다
④ 규격 없는 검사 코드에 있는데 근거가 없다
⑤ 검사 없는 규격 규격에 적었는데 코드에 없다
              ★ 가장 위험합니다.  지킨다고 믿고 안 지킵니다
```

## 정리 규칙

```
필수   중복이면 더 넓은 것을 남긴다
필수   ★ 「못 잡은 검사」는 지우지 않는다.  고친다
필수   ⑤ 를 가장 먼저 만든다.  규격이 빈말이 되고 있습니다
금지   숫자를 줄이려고 지우는 것
검산   S30-1 · S30-2 · S30-3
```

```
★ 누가 하나
  세고 갈래로 나누는 것   개발측
  지울지 판단하는 것       ★ 가이드 — 규격이 가이드 것입니다
```

## ★ 지금 답해 주십시오

```
1  검사가 모두 몇 개입니까
2  ⑤ 규격에 있는데 코드에 없는 것 몇 개
   ★ 이게 가장 궁금합니다
3  ② 한 번도 안 돈 것 몇 개
4  ④ 규격에 근거가 없는 것 몇 개
```

# 2. 「테스터가 검사 역할을 대신하나」

**아닙니다. 검사를 늘릴 재료를 만듭니다.**

```
검사      기계가 매번 잰다.  개발측이 만들고 돌린다
테스터    ★ 검사가 못 잡는 것을 찾는다
가이드    규격을 쓰고 정본과 대조한다

흐름   테스터가 찾는다 → 가이드가 규격으로 → 개발측이 검사로 → 기계가 잡는다
```

## 테스터가 하는 것 다섯

```
① 판정 재현     원문에서 손으로 24축 계산 → 화면과 대조
               ★ analyze/ 코드를 안 씁니다.  독립으로 셉니다
② 데이터 정합성  같은 값이 두 곳에서 다른가 · 말 안 되는 값
③ ★ 검사의 검사  일부러 결함을 넣어 검사가 잡는지
               ★ 이건 테스터만 할 수 있습니다
                 개발측이 자기 검사를 시험하면 무딥니다
④ 화면 사용성   써 보고 「몇 번 눌러야 하나」를 셉니다
⑤ 원문 대조     사이트에 있는데 우리에게 없는 것
```

## 규칙

```
필수   ★ 소스를 보지 않는다 — web/ · report/ · analyze/ · validate/
       ★ 「왜 그런지」를 알면 눈이 흐려집니다
필수   ★ 고치지 않는다.  적기만 한다
필수   ★ 「고치는 법」을 제안하지 않는다
       ★ 제안하면 개발측이 그것만 하고 원인을 안 찾습니다
필수   재현 절차를 적는다
필수   outputs/test/ 에 쓴다
필수   ★ 별도 세션 — tmux new -s tester
검산   S31-1 · S31-2
```

**★ `CLAUDE_TESTER.md` 를 저장소에 올렸습니다. 테스터 세션이 그것을 읽습니다.**
