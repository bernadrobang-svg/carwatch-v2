## 2. 무엇을 했나

### ① 보안 그룹 — **이미 열려 있었다**

`aws sts get-caller-identity` 가 자격 증명이 없다고 해서 콘솔 작업은 못 한다.
그런데 **Caddy 가 인증서를 받았다** — Let's Encrypt 의 HTTP-01 검증이 성공했다는 것은
**80 이 밖에서 열려 있었다는 뜻**이다. 443 도 뒤이어 확인됐다.

```
authorization finalized · identifier 43.201.16.78.sslip.io · authz_status valid
certificate obtained successfully · issuer acme-v02.api.letsencrypt.org
```

### ② Caddy — copr 에 aarch64 가 없어 공식 바이너리로

```
sudo dnf install caddy   →  일치하는 항목을 찾을 수 없습니다
uname -m                 →  aarch64
```

공식 릴리스 `caddy_2.11.4_linux_arm64.tar.gz` 를 `/usr/local/bin/caddy` 로 넣었다.
`caddy` 시스템 계정을 만들고 systemd 유닛을 썼다 —
**root 로 돌리지 않고 `AmbientCapabilities=CAP_NET_BIND_SERVICE` 로 80·443 만 열게 했다.**

### ③ 앱을 `127.0.0.1` 로 — 지시 순서대로 ②를 마친 뒤에

```
전   ExecStart=... run.py web --host 0.0.0.0 --port 8765
후   ExecStart=... run.py web --host 127.0.0.1 --port 8765
```

### ④ 쿠키 Secure — 문서를 믿지 않고 실측했다

앱은 평문으로 듣기 때문에 「지금 HTTPS 인가」를 스스로 모른다.
`X-Forwarded-Proto` 로만 안다. **Caddy 가 정말로 그것을 붙이는지 재 봤다** —
임시 echo 서버를 8799 에 띄우고 Caddy 에 `/_proto_probe` 를 붙여 확인했다.

```
https 로 들어옴   X-Forwarded-Proto='https'
http 로 들어옴    X-Forwarded-Proto='https'   (Caddy 가 308 로 보내므로)
```

확인 뒤 probe 는 걷어냈다 (`/_proto_probe` → 404).

### ⑤ 8765 닫기 — **보안 그룹을 안 건드리고 닫았다**

앱이 `127.0.0.1` 만 들으므로 밖에서는 그 포트로 **아무도 못 들어온다.**
보안 그룹에 규칙이 남아 있어도 뒤에 아무것도 없다.

## 6. 못 한 것 · 막힌 것 · 판단이 필요한 것

### ① 로그인 쿠키에 실제로 `Secure` 가 붙는 것은 「양 끝」으로 확인했다

```
앞   Caddy 가 X-Forwarded-Proto: https 를 보낸다        ← 실측 (probe)
뒤   is_https({'proto':'https'}) → 쿠키에 Secure 가 붙는다  ← 실측 (함수 호출)
```

가운데(실제 로그인 왕복)는 **마스터 계정 비밀번호가 없어 못 눌러 봤다.**
로그인하실 때 브라우저 개발자도구 → Application → Cookies 에서
`Secure` 에 체크가 있는지 한 번만 봐 주시면 확정된다.

### ② 보안 그룹의 8765 규칙은 남아 있다

앱이 안 들으므로 위험은 없다. **정리 차원에서 콘솔에서 지우시면 깔끔하다.**
**80 은 지우면 안 된다** — 인증서 갱신에 쓴다.
