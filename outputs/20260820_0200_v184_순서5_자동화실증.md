## 3. ★ 실증 — 「recalc 성공 0건」은 더 이상 사실이 아닙니다

### ① 04:00 자동 실행이 **성공했습니다** (08-19)

```
sudo journalctl -u carwatch-daily
 8월 19 04:00:36  Starting carwatch-daily.service …
 8월 19 04:00:36  하루치를 큐에 넣었습니다 — ee40ff61
 8월 19 04:00:36  Finished carwatch-daily.service
```

```
recalc_job  ee40ff618dfb5747
  trigger  schedule       reason  raw_missing      scope  all
  queued   2026-08-18T19:00:36Z  (= 08-19 04:00 KST)
  ended    2026-08-18T21:49:01Z  (= 08-19 06:49 KST · 2시간 48분)
  status   done
  detail   S5 ok 21,946 · S6 ok 71,273 · S9 ok 85,320
```

★ **큐에 넣은 것만이 아니라 소비기가 꺼내 2시간 48분을 돌고 끝냈습니다.**

### ② ★★ 그런데 그 뒤로 자동화가 통째로 막혀 있었습니다

```
recalc_job  c27c0f4d32cf5300ed
  queued   2026-08-18T21:55:32Z (= 08-19 06:55 KST)
  status   running       ended  없음        ★ 28시간째
```

이것은 **제가 08-18 에 죽인 실행**입니다 (`listing_updated` 를 잘못 돌려 4분 만에 끊었습니다).
`daily_enqueue` 는 「이미 도는 것이 있으면 건너뛴다」라서,

```
★ 이 하나가 다음 04:00 부터 영원히 자동화를 막습니다
★ 큐만 보면 「도는 중」이라 아무도 안 놀랍니다 — S42 ①「조용히 틀린다」
```

### ③ 13:00 이 반영돼 있지 않았습니다

```
개정 388   자동 수집은 13:00 — config.collect_daily_at
실제       config/admin.json  "04:00"
           deploy/carwatch-daily.timer  OnCalendar=04:00
           /etc/systemd/system/…       OnCalendar=04:00
```

★ **개정 388 이 규격에만 있고 아무 데도 안 들어가 있었습니다.**

## 4. 무엇을 했나

### ① 13:00 으로 맞췄습니다

```
config/admin.json            collect_daily_at  04:00 → 13:00 · daytime_hours [9,18]
deploy/carwatch-daily.timer  OnCalendar        04:00 → 13:00
/etc/systemd/system/…        같은 파일을 넣고 daemon-reload
```

### ② 끊긴 실행을 닫습니다 — `reap_stale_jobs()` (`store/adminops.py:570`)

```
config/admin.json  job_stale_hours = 6
daily_enqueue      큐에 넣기 **전에** 끊긴 것을 닫는다
★ 지우지 않는다.  실패로 닫고 왜 그런지 적는다 — 흔적이 남아야 한다
```

### ③ ★ 리퍼가 **살아 있는 실행을 죽이지 않게** 했습니다

실측 중에 알았습니다 — **도는 작업의 `updated_at` 이 안 움직입니다.**

```
05:35:57  raw 106,562  ·  작업 updated_at 05:35:35
05:36:42  raw 106,687  ·  작업 updated_at 05:35:35   ← 45초에 원문 +125행
```

`updated_at` 만 보면 6시간 뒤 이 **살아 있는 실행**을 죽입니다.
규격이 이미 답을 적어 뒀습니다 (`c-tools.md:585`).

```
필수   판단 근거를 셋 다 본다
       ① recalc_job 에 running 이 있는가
       ② raw_response 가 최근 N초에 늘었는가
       ③ 마지막 처리 시각이 N초 안인가
```

```
고침   원문이 상한 안에 늘었으면 아무것도 안 닫는다 — 도는 중이다
```

## 5. 왜 그렇게 했나

```
① 「돌았다」를 큐로 증명하지 않았다.  raw_response 가 45초에 125행 는 것을 쟀다
   ★ 지시가 「큐만 보지 않는다」라 했고, 규격이 판단 근거 셋을 이미 적어 뒀다
② 끊긴 작업을 지우지 않고 실패로 닫았다.  지우면 왜 막혔는지가 사라진다
③ 리퍼에 원문 증가를 넣었다.  안 넣으면 이 도구가 마스터의 긴 수집을 죽인다 —
   ★ 되돌릴 수 없는 것을 만드는 셈이다
④ 시각을 코드가 아니라 config 에 두고, 타이머 파일에 「정본은 config」라 적었다.
   둘이 갈리면 V10-31 이 잡는다
```

## 10. 못 한 것 · 막힌 것 · 여쭐 것

### 여쭐 것 ①  ★ 도는 작업이 `updated_at` 을 안 갱신합니다

```
45초에 원문 125행이 느는데 recalc_job.updated_at 은 그대로다
current_step · step_done · step_total 도 전부 NULL 이다
```

규격(`c-tools.md:585`)은 「마지막 처리가 N분 전이면 「N분째 진척 없음」이라 적는다」를
요구합니다. **소비기가 진행을 안 적고 있습니다.** 지금은 원문 증가로 우회했지만,
화면의 진행 표시는 여전히 비어 있습니다. **소비기에 진행 기록을 넣을까요.**

### 여쭐 것 ②  `V1-11` 이 남습니다

`actual` 이 「0단계」입니다 — 이번 `check_all` 이 자기 `run_id` 로 남긴 단계가
없다는 뜻입니다. **지금 도는 실행이 끝나면 다시 재겠습니다.**

### 여쭐 것 ③  타이머를 바꾸자 즉시 한 번 돌았습니다

`Persistent=true` 라 오늘 13:00 몫을 따라잡았습니다. **의도한 것은 아닙니다.**
결과적으로 순서 5 의 실증이 됐고, `raw_missing` 이라 없는 것만 받습니다
(제가 08-18 에 낸 사고 — `listing_updated` 전건 재수집 — 와 다릅니다).
★ **지금도 돌고 있습니다.** 끝나면 숫자를 다시 내겠습니다.

### 못 한 것

**순서 7(추정 ~ 503건을 층 하나씩 ✓ 로)** 이 남았습니다.
