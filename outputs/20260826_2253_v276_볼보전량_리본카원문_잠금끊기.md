## 4. ★★★ 잠금이 또 물었다 — 뿌리를 마저 잡았다

### 4-1. 무슨 일이 있었나

```
볼보 137건 → 재판정(S5~) 시작 → 그 사이에 리본카 수집기를 돌렸다
  sqlite3.OperationalError: database is locked
    File "tools/collect_reborncar.py", line 126, in main
      save_site_raw(...)
```

★ v273 에서 `busy_timeout 30000` 과 `db_batch_commit_rows 200` 을 넣었는데도 물었다.
★ 재 봤다 — **쓰기 0/6 · 8초씩 기다리고 다 실패.**

### 4-2. 까닭 — ★ `commit()` 은 「쓴 행」에서만 불린다

```
store/raw.commit()  ← batch 안에서 200행마다 끊는다
그런데 그것은 ★ **쓴 행**에서만 불린다
  upsert_core 는 ★ 바뀐 것이 없으면 ★ 일찍 돌아간다 — ★ commit 을 안 부른다
  그런데 ★ 앞서 쓴 것 때문에 ★ **트랜잭션은 열려 있고** ★ 잠금은 그대로다
★ 볼보를 받은 뒤 S6 이 ★ 엔카 13만 행을 ★ **다시 파싱**했다 —
  ★ 대부분 안 바뀌므로 ★ commit 이 거의 안 불렸다.  ★ 그래서 잠금이 안 끊겼다
```

### 4-3. 고친 곳

| 파일 | 무엇 |
|---|---|
| `store/raw.py` | `tick(conn, rows)` — ★ **처리한 행 수**로 끊는다 (쓴 행이 아니라) |
| `collect/runner.py` | S4·S6 의 진행 표시 자리에서 `raw_tick(conn, n)` 을 부른다 |

★ 진행 표시는 20행마다 불린다. ★ `tick` 은 **행 번호**를 받아 200행마다 끊는다 —
★ 셈으로 세면 4,000행이 되어 **창이 10초에 한 번밖에 안 열린다** (그래서 행 번호로 받는다).

```
확인 (단위 시험)  4,000행 동안 ★ 21번 끊었다 (200행마다 + 끝 1번)
```

## 5. ★★ 또 하나 — 재시작이 재판정을 ★ 영영 멈춰 세우고 있었다

### 5-1. 1차 결과

```
recalc_job  7c2706f3  status='running'   ← ★ 그대로 멈춰 있었다
carwatch 로그  아무것도 안 나온다
```

★ 소비기는 **데몬 스레드**다. 서버를 재시작하면 돌던 작업이 그 자리에서 죽는데
**줄의 `status` 는 `running` 그대로** 남는다.
★ `take_next` 는 **`queued` 만** 집으므로 — ★ **그 작업은 영영 안 돈다.**

★ 볼보 137건 재판정이 그렇게 멈춰 있었다. **내가 재시작한 탓이다.**

### 5-2. 고친 곳

| 파일 | 무엇 |
|---|---|
| `collect/worker.py` | `reclaim_stale()` — 뜰 때 한 번, 버려진 `running` 을 `queued` 로 되돌린다 |

★ 프로세스가 죽으면 **아무도 그것을 쥐고 있지 않다.**
★ 한 프로세스에 하나만 도는 규칙이라 **남의 것을 뺏지 않는다.**
★ 잃는 것은 없다 — 원문이 남아 있어 다시 파싱하면 된다.

```
확인 (단위 시험)  running 1건 · done 1건 → ★ 되살린 건수 1 · [(x,queued),(y,done)]
확인 (배포)      재시작 뒤 updated_at 이 22:33:11 로 바뀌었다 —
                되살아나 곧바로 다시 집혔다.  ★ 재판정이 끝까지 돌았다
```

★ ★ 내가 `start()` 에 없는 `clock` 을 쓰는 실수를 했고 **돌리기 전에 잡아 고쳤다.**
