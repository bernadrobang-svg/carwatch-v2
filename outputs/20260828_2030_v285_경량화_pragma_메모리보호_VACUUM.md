## 2. 먼저 잰 것 — 무게가 어디에 있나

### ① DB 가 램에 안 들어간다.  그것이 전부다

```
실측 — 현황(/) 을 관리자 계정으로 · 매번 새 연결로
  DB 페이지 캐시가 차가울 때   10.16초
  DB 페이지 캐시가 더울 때      0.71초
```

★ **14배다.**  ★ 그러므로 「DB 가 캐시에 남아 있느냐」가 사실상 유일한 변수다.

```
램 1,841MB · DB 1.26GB → ★ 안 들어간다.  ★ 크롤러가 훑을 때마다 밀려난다
```

### ② mmap 은 지렛대가 아니었다 — ★ 내가 처음에 틀렸다

```
처음 잰 것   mmap 0 → 12.14초 · mmap 256MB → 0.83초   ← ★ 캐시가 데워진 것이었다
다시 잰 것   요청 12번 뒤 RSS   mmap 없이 +12.8MB · mmap 켜고 +12.0MB
```

★ **메모리도 시간도 의미 있게 안 줄었다.**  ★ 그래서 `mmap_size` 는 **안 넣었다.**
★ 앞 보고(v284 7항)에서 「연결 재사용/mmap 이 답」이라 적은 것을 ★ 이것으로 정정한다.
★ 참인 것은 「연결마다 캐시가 빈다」가 아니라 **「DB 가 램에 안 들어간다」**였다.

## 3. 무엇을 했나 — 셋

### ② systemd — 마스터 화면을 굶기지 않는다

`/etc/systemd/system/carwatch.service.d/10-memory.conf` (새 파일)

```

OOMScoreAdjust=-500   마지막에 죽는다.  내 도구·claude 가 먼저 죽는다
★ MemoryMax 는 안 둔다 — carwatch 를 죽이는 것이 목적이 아니다
```

★ 근거 — 08-21 21:53 전역 OOM.  `Free swap = 0kB`.
  ★ OOM 이 죽인 것은 carwatch 가 아니라 claude 였는데,
  ★ 그때 carwatch 는 **RSS 2.7MB · 스왑 598MB** 였다 —
  ★ 죽지 않고 **통째로 스왑에 밀려 못 움직였다.**  마스터에겐 그것이 「죽음」이다.

```
확인   memory.min       201,326,592 (192MB) — ★ 재시작 없이 곧바로 걸렸다
       oom_score_adj    -500 — ★ 재시작 뒤 붙었다
```
