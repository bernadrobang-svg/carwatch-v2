## 2. 어떻게 쟀나 — ★ 「따뜻한 캐시」로 재면 안 보인다

처음엔 `/` 가 0.7초로 나왔다.  검사는 15.8초라 했다.  **둘 다 참이었다.**

```
같은 화면을 세 번 불렀다   0.73 · 0.69 · 0.70 초
새 프로세스에서 한 번      18.30 초
```

까닭은 운영체제의 페이지 캐시다.  `carwatch.db` 는 **1.1GB** 다.
한 번 읽고 나면 메모리에 남아 두 번째부터 빠르다.
**마스터가 겪는 것은 첫 번째다** — 내가 `systemctl restart carwatch` 를
할 때마다 마스터의 첫 화면이 18초였다.

그래서 이렇게 쟀다.

```
sudo sh -c 'sync; echo 1 > /proc/sys/vm/drop_caches'
그 뒤 한 번만 부른다
```

★ 그리고 쿼리마다 시간을 찍어 **어느 한 줄이 먹는지**를 봤다.

## 3. 무엇이 나왔나 (1차 결과 · 고치기 전 숫자)

| 화면 | 한 쿼리 | 걸린 시간 |

```
raw_response 의 origin  collector 143,799 · browser 3,223 · import 1
```

**딱 1건**을 찾으려고 14만 7천 행을 뒤에서부터 훑었고,
`body`(원문 몸통)까지 읽었다.  파일 1.1GB 의 대부분이 그 몸통이다.


## 6. 못 한 것 · 판단이 필요한 것

### ★ 가이드에 여쭐 것 — `/listings` 306KB (상한 300KB)

```
전체 252KB (내 계정) ~ 306KB (관리자)
  거르개까지  14KB
  카드 50장  238KB   ★ 한 장에 4,882B
```

★ 색인으로 줄일 수 있는 것이 아니다.  **한 쪽에 몇 장을 낼 것인가**의 문제다.

```
ⓐ 한 쪽 50장 → 40장    ★ 마스터가 보는 것이 바뀐다
ⓑ 상한 300KB → 320KB   ★ 「고치기 싫어 상한을 올렸다」가 된다.  안 한다
ⓒ 카드의 곁말(title=)을 줄인다  ★ 손가락으로 볼 때 쓰는 설명이 사라진다
```

★★ 셋 다 **마스터가 보는 화면이 바뀐다.**  규칙 2 대로 **내가 정하지 않았다.**

### ★ `/admin/registry` 는 색인 문제가 아니다

```
SELECT body FROM raw_response WHERE endpoint=? AND status='ok'
 ORDER BY (id * 2654435761) % 1000003 LIMIT ?     ← 표본을 골고루 뽑는 계산식
```

★ 계산식으로 정렬하므로 색인을 못 탄다.  **표본을 뽑는 방식 자체**가
그렇게 만들어져 있다 (등록부는 원문 몸통을 봐야 만들어진다).
★ 지어내 고치지 않았다 — 표본 방식을 바꾸면 등록부 결과가 바뀐다.

```
여쭙는다   등록부 표본을 「무작위」가 아니라 「최근 N건」으로 바꿔도 되나
```
