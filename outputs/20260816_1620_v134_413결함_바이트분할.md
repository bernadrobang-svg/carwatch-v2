## 2. 무엇을 했나 — 먼저 **재고** 고쳤다

### ★ 결함 2 는 결함이 아니었다 — 「391쪽」은 맞는 숫자였다

DB 를 세었다.

```
browser 원문 행 392건 (전부 endpoint='list')
크기   최소 2,263 · 최대 26,252 · 평균 22,937 글자
```

**392쪽이 실제로 저장돼 있었다.** 화면의 「저장 391쪽」은 정확했다.
「전 차종이 하나도 저장되지 않았습니다」가 사실이 아니었고,
그렇게 읽히게 만든 것이 결함 3(표시 순서)이다.

### ★ 결함 1 의 진짜 원인 — 건수로 나누면 바이트가 안 묶인다

「통째로 보냈다」가 아니었다. **쪽 단위로 보냈고, 그 쪽이 상한을 넘었다.**

```
1쪽 = 20건
저장된 쪽 최대   26,252글자 = 27,758바이트   ← 한글은 글자당 3바이트다
실패한 쪽        그보다 컸다 (사진·옵션이 많은 차종)
상한             65,536바이트
```

지시서의 「1쪽 20건이면 약 13KB」는 **글자 수 기준**이고, 실제로 가는 것은 **바이트**다.
차종마다 사진·옵션 배열 길이가 달라 같은 20건이라도 크기가 배 이상 차이난다.

실측으로 상한 자체는 확인했다 — 실제 저장된 원문으로 두 번 눌렀다.

```
27,758바이트 멀티파트 POST → 303 (저장됨)
55,516바이트 멀티파트 POST → 303 (저장됨)
raw_response browser 392 → 394
```

**65,536 까지는 들어간다. 그보다 큰 쪽만 413 이었다.**
(이 시험 2행은 꾸며 낸 원문이므로 확인 뒤 걷어냈다 — 394 → 392)

## 6. 못 한 것 · 막힌 것 · 판단이 필요한 것

### ① 브라우저 동작은 마스터가 눌러야 확정된다

JS 는 서버에서 못 돌린다. 서버 쪽(상한·저장·검사)은 실측했고, 나누는 로직은
코드와 검사로만 확인했다. **다시 눌러 주십시오.**

전 차종을 한 번에 하기 전에 **`KOLEOS_HEV` 하나로 먼저** 해보시길 권한다 —
로직이 맞는지 짧게 확인되고, 그다음 전 차종이 안전하다.

### ② facet 이 아직 0건이다

`browser` 원문 392건이 **전부 목록**이다. facet 은 한 건도 안 들어왔다.
facet 응답이 상한을 넘었을 가능성이 있는데, facet 은 **건수로 나눌 수 없다.**
이번에 그 경우 화면이 이렇게 말하도록 했다.

```
facet 이 N바이트 — 나눌 수 없습니다
```

**그 숫자가 나오면 알려 주십시오.** 그때는 규격 판단이 필요하다 —
`max_form_bytes` 를 올릴지, facet 을 `inav` 축별로 나눠 부를지.
`V4-25`·`V3-30`·`V3-32` 가 여기에 걸려 있다.
