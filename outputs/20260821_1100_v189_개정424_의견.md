# ★★ 먼저 — 가이드 판단이 틀린 곳 넷

## ① 「result_axis 에 축 점수가 앉아 있으니 배점만 곱하면 된다」 — **틀렸습니다**

```
스키마를 열었습니다 (sql/ddl/04_result.sql:4)
  result_axis(listing_id, calc_version, dict_version, axis,
              value INTEGER, source, prio, excluded,
              max_points REAL, score REAL)
```

```
★ value 는 **절대점수**입니다.  충족률이 아닙니다
  실측 — value.market 은 −100 ~ +100, state.accident 는 0 ~ 40,
        taste.color 는 3 ~ 10.  전부 그 축의 배점 범위입니다
```

드릴 뻔했습니다.

# 2. 재계산 — 묻는 것 넷

## 2-1. 갈래 배점만 바꾸면 recalc 를 돌려야 하나

**돌려야 합니다.** 위 ①②가 근거입니다.

```
드는 것   S9(판정) 7.1초 + S10(등급) 2.9초 = ★ 약 10초 (전건 3,841매물 · 92,184축)
        ★ 수집 없음.  엔카를 안 부릅니다
걸리는 것  없습니다.  10초는 「돌려야 하나」를 고민할 값이 아닙니다
```

★ **의견** — 「배점을 바꾸면 recalc」를 규칙으로 못 박으시면 됩니다.
지금 재처리 결정표에 `scoring → S10 만` 이라 적혀 있는데(개정 315),
**갈래 배점이 바뀌면 S10 만으로는 안 됩니다.** S9 부터여야 합니다.
★ 이것이 규격의 오류입니다 — 고쳐 주십시오 (`docs/chapters/13-pipeline.md:302`).

## 2-2. 축 온·오프를 recalc 없이 화면에서 할 수 있나

**할 수 있습니다. 무겁지 않습니다.**

```
실측
  전건 축 행 92,076 읽기            206ms
  선루프 뺀 전건 재집계 (3,841건)     ★ 49ms
  한 쪽(200건) 재집계               ★ 3ms
```

```
★ 200건 × 24축은 SQL 한 번이면 3ms 입니다.  더할 것도 없습니다 —
  SUM(value) · SUM(max_points) 를 GROUP BY listing_id 로 냅니다
★ 분모도 함께 줄어듭니다 (SUM(max_points) 가 675 → 665)
```

**어디에 두는 것이 낫나** — `store/core.py` 에 조회 하나로 둡니다.

```
이유   화면이 SQL 을 짓지 않는다 (V11-01)
      세는 것과 뽑는 것이 같은 조건을 써야 건수·쪽이 안 어긋난다 (V11-55)
★ 등급까지 즉시 바꾸려면 grade_cuts 를 같이 적용해야 합니다 —
  그 계산은 score/grade.py::grade_of 하나뿐이라 재사용됩니다
```

★ **걸리는 것 하나** — 축을 끄면 **등급이 바뀝니다.** 그러면 「화면에서 본 등급」과
`result_score.grade` 가 달라집니다. 어느 쪽이 정본인지 정해 주셔야 합니다.

```
갈래 A   화면 것은 「미리보기」다.  저장 안 함 — 값싸고 되돌리기 쉽다
갈래 B   끈 것을 config 에 저장하고 recalc 를 돌린다 (10초) — 정본이 하나가 된다
★ 개발측 의견 — B 를 권합니다.  A 는 「화면과 DB 가 다른 등급을 말한다」가 되고
  그것이 이 프로젝트가 막으려는 「선언과 실제의 괴리」입니다
```

## 2-3. 점수 필터를 SQL 로 걸 수 있나

**갈래 합이 없어서 지금은 못 겁니다. 그러나 SQL 로 만들 수 있고 빠릅니다.**

```
실측
  갈래 합 전건 집계 (3,841건)        ★ 66ms
  「값 220 이상」 필터                ★ 25ms
```

```sql
SELECT listing_id FROM result_axis WHERE excluded=0 GROUP BY listing_id
 HAVING SUM(CASE WHEN axis LIKE 'value.%' THEN value ELSE 0 END) >= 220
```

★ **V11-55(건수·쪽이 어긋난다)는 안 걸립니다.** 위 SQL 을 `_listings_where` 의
서브쿼리로 넣으면 **세는 것과 뽑는 것이 같은 조건**이 됩니다.

```
★ 다만 권하는 것 — result_score 에 갈래 합 네 칸을 둡니다
  group_car · group_value · group_warranty · group_taste
드는 것   DDL 4칸 + S10 이 쓸 때 함께 넣기.  ★ 이미 더하고 있는 값입니다
얻는 것   ① 필터가 JOIN 없이 걸린다  ② 목록의 막대 넷을 한 번에 읽는다 (시안 3-1)
        ③ 「갈래 합 = 갈래 표기」를 V3-77 이 DB 에서도 잰다
```

```
★ 「사라짐 201건」을 세기만 한다 — 맞습니다.  다만 **재료는 다 있습니다**
```

### ★ 걸리는 것 하나 — 「그때의 등급」이 안 남습니다

```
result_score 는 (listing_id, calc_version) 이 PRIMARY KEY 입니다
calc_version 이 'c1' 하나뿐이라 recalc 를 돌리면 **덮어씁니다**
★ 실측 — 어제 recalc 후 옛 점수를 되찾지 못했습니다 (v188 §7 에 적었습니다)
```

**→ 사라진 시점의 등급을 남기려면 「사라질 때 한 줄 떠 두는」 표가 필요합니다.**

```
권하는 것   listing_gone (listing_id, vehicle_id, gone_at, days_on_market,

쌓이는 속도  실측 — 어제 하루에 「사라짐 201건」.  ★ 한 달이면 6,000건쯤
```

★ **개발측 의견 — 이것을 가장 먼저 만드시길 권합니다.**

```

      ② ★ 오늘 안 만들면 오늘 사라진 201건은 영영 못 되찾는다.
```
